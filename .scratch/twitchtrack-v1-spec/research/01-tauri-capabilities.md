# Research: Tauri capabilities for tray, notifications, autostart, single-instance

## 1. System tray

Tray icons are core `tauri` API, gated behind the `tray-icon` Cargo feature, built with `TrayIconBuilder` ([System Tray docs](https://v2.tauri.app/learn/system-tray/)). Menus are built with `tauri::menu::Menu` / `MenuItem::with_id(app, id, text, enabled, accelerator)`, so each item gets an explicit string `id` (e.g. `"hide"` vs `"quit"`). The menu handler (`.on_menu_event(|app, event| match event.id.as_ref() { "quit" => ..., "hide" => ... })`) dispatches purely on that id, so "Hide" and "Quit" are trivially distinguishable actions on the same menu ([System Tray docs](https://v2.tauri.app/learn/system-tray/)). Tray icons also emit their own pointer events — `TrayIconEvent::Click`, `DoubleClick`, `Enter`, `Move`, `Leave` (with button/button-state) — via `.on_tray_icon_event()`, independent of the menu, which is the usual hook for "left-click tray icon shows/focuses window" ([System Tray docs](https://v2.tauri.app/learn/system-tray/)).

## 2. Desktop notifications: click handling

`@tauri-apps/plugin-notification` (`tauri-plugin-notification`) exposes `sendNotification`, `onNotificationReceived`, `registerActionTypes`, and `onAction` ([Notification plugin docs](https://v2.tauri.app/plugin/notification/); [guest-js source](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/notification/guest-js/index.ts)). However, the docs state explicitly: **"The Actions API is only available on mobile platforms"** ([Notification plugin docs](https://v2.tauri.app/plugin/notification/)) — `registerActionTypes`/`onAction`, including the `foreground`-on-action-tap behavior, work on Android/iOS but not Windows/macOS/Linux. Confirmed in source: the desktop backend (`plugins/notification/src/desktop.rs`) wraps the `notify-rust` crate and only builds/shows the notification; it wires no click/interaction callback back to the frontend at all. `Options.extra` does exist as an arbitrary-payload field, but with no desktop click event to receive it, it's unusable for this purpose on desktop. Windows notifications also only work for installed (not `tauri dev`) builds, per the same docs page. **Practical implication for the ticket:** clickable desktop notifications that jump to a Watched Streamer are not deliverable via this plugin on desktop; the tray icon click event (§1) or the single-instance/deep-link mechanisms are the realistic focus/routing hooks instead.

## 3. Autostart (start on login)

Official plugin: `tauri-plugin-autostart` (`@tauri-apps/plugin-autostart`), supported on Windows/Linux/macOS, not mobile ([Autostart plugin docs](https://v2.tauri.app/plugin/autostart/)). JS API: `enable()`, `disable()`, `isEnabled()`. Rust init takes a `MacosLauncher` (`LaunchAgent` default, or `AppleScript`) plus optional launch args ([Autostart plugin docs](https://v2.tauri.app/plugin/autostart/); [lib.rs source](https://github.com/tauri-apps/plugins-workspace/blob/v2/plugins/autostart/src/lib.rs)). Per-platform mechanism differs: Windows uses a registry run-key, macOS a LaunchAgent plist (or an AppleScript-based login item), Linux an XDG `.desktop` autostart entry / AppImage path detection — all handled internally by the plugin, no extra platform code needed by the app.

## 4. Single-instance enforcement

Official plugin: `tauri-plugin-single-instance`, Windows/macOS/Linux only, **must be the first plugin registered** in the builder ([Single Instance docs](https://v2.tauri.app/plugin/single-instance/)). `tauri_plugin_single_instance::init(|app, args, cwd| { ... })` — the callback fires in the already-running instance and receives the new launch's `args: Vec<String>` and `cwd: String`, so the standard pattern is `app.get_webview_window("main").unwrap().set_focus()` in that closure instead of letting the second process open a window ([Single Instance docs](https://v2.tauri.app/plugin/single-instance/)). On Linux it works via DBus; Flatpak/Snap packaging needs an explicit `DBUS_ID` if the app id differs from the package id.
